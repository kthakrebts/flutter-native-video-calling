# Advanced Troubleshooting & Debugging Manual

This document provides a highly technical debugging reference for senior engineers maintaining this RTC infrastructure. It details common runtime bugs, platform-specific anomalies, integration errors, and how to debug them using native tooling.

---

## 1. Android Permission Handling & API 31+ Mismatches

Android's runtime permissions system has become increasingly strict across different OS versions, especially concerning real-time media and wireless peripheral access.

### Symptoms
- Permission checking returns `false` even though the user accepted standard dialogs.
- Instant crash with `SecurityException` when attempting to connect to a room.
- Audio fails to route to Bluetooth headsets/earphones.

### Root Cause Analysis
Starting with **Android 12 (API 31)**, wireless audio routing is governed by the `BLUETOOTH_CONNECT` permission. In **Android 13 (API 33)**, local foreground notifications (used to keep active WebRTC calls alive when backgrounded) require `POST_NOTIFICATIONS`. If these are not requested dynamically or declared in the manifest, the system denies hardware access.

### Resolution Strategy
The manifest and Kotlin controller must match permissions by API level. We implement this in `MainActivity.kt`:

```kotlin
private fun hasPermissions(): Boolean {
    val requiredPermissions = mutableListOf(
        Manifest.permission.CAMERA,
        Manifest.permission.RECORD_AUDIO
    )

    // Bluetooth connection required for audio routing on API 31+
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
        requiredPermissions.add(Manifest.permission.BLUETOOTH_CONNECT)
    }

    // Post notifications required for foreground services on API 33+
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
        requiredPermissions.add(Manifest.permission.POST_NOTIFICATIONS)
    }

    return requiredPermissions.all { permission ->
        ContextCompat.checkSelfPermission(this, permission) ==
                PackageManager.PERMISSION_GRANTED
    }
}
```

## 2. Twilio Token Expiration & Connection Failures

WebRTC signaling sessions rely on cryptographically signed JSON Web Tokens (JWT) generated by a secure backend server.

### Symptoms
- Native logs emit: `❌ Failed to connect to room: TwilioException (code: 20101, Access Token expired)`
- Instant connection drops on room join.

### Root Cause Analysis
Twilio Access Tokens have a default lifetime (typically 1 hour). If a token is expired, or if the token signature is invalid, or if there is a mismatch between the token's configured **Room Grant** and the target room type (e.g., attempting to join a Group room with a Peer-to-Peer room token), Twilio’s authentication gateways will reject the socket handshake with error code **20101** or **20105**.

### Resolution & Diagnostic Checklist
1. **Time Drift:** Check if the host device's local clock has drifted significantly from network time. JWT validation is highly sensitive to system clock drift.
2. **Backend Validation:** Verify the token generation logic on your backend. Ensure the signature is generated using the exact Twilio API Key Secret (which starts with `SK...`), not the account's master Auth Token.
3. **Room Type Matching:** In the Twilio Developer Console, ensure the room type ("Group", "Go", "Peer-to-Peer") matches the configuration under which the room was generated.

## 3. Black Screens, Video Freezing & Rendering Issues

Platform View composition can occasionally fail to draw frames, presenting a blank or black canvas to the user.

### Symptoms
- Local video preview is black, but the remote participant can see the stream.
- Audio works perfectly, but the remote video view remains black indefinitely.
- Video freezes permanently when the screen orientation changes.

### Root Cause Analysis
1. **Unattached Sinks:** The native `VideoView` layout has been initialized, but the media track hasn't attached the view as a frame consumer via `track.addSink(view)`.
2. **Race Conditions during Layout:** In a hybrid framework, the native `AndroidView` is created asynchronously. If the Twilio connection listener fires `onConnected` before the Flutter widget has fully registered its layout view, the Kotlin code tries to call `.addSink()` on a null reference.
3. **OpenGL Context Loss:** Device orientation changes or minimizing the app can force the OS to destroy the OpenGL drawing surface. When restored, the track continues to emit frames to the dead surface.

### Resolution & Diagnostic Flow
To address this, we decouple view registration from connection states by caching the tracks and views. The factory handles registration explicitly on initialization:

```kotlin
fun setLocalVideoView(view: VideoView) {
    localVideoView = view
    // Attach existing track immediately if it has already been instantiated
    localVideoTrack?.addSink(view)
    Log.d(TAG, "✅ Local VideoView registered and track attached")
}
```

If a track is generated *before* the Platform View finishes inflating, the factory registers the view, and the native bridge instantly binds the track to the freshly mounted OpenGL surface, eliminating race-condition black screens.

## 4. Platform View Disposal & Zombie Thread Crashes

Improperly managing the native-hybrid boundary is the primary cause of fatal app crashes in production Flutter apps.

### Symptoms
- App crashes randomly 2-3 seconds after a call is terminated and the user exits the page.
- Logcat emits a fatal signal: `Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x...`
- High CPU usage continues even after the call page is popped from the navigation stack.

### Root Cause Analysis
When a Flutter widget is popped, the Dart GC instantly reclaims the Dart components. However, the native Android thread pools and background WebRTC rendering engines are still running. If a background WebRTC thread attempts to push a decoded video frame to a `VideoView` whose underlying OpenGL context or `SurfaceView` window was destroyed during Flutter's layout disposal, the app will instantly crash with a Segmentation Fault (SIGSEGV).

### Resolution Strategy
The `PlatformView.dispose()` implementation must synchronously and thoroughly dismantle the media pipeline. In `TwilioVideoViewFactory.kt`:

```kotlin
override fun dispose() {
    Log.d(TAG, "🗑️ Remote video view disposed")
    mainActivity.clearRemoteVideoView()
}
```

In `MainActivity.kt`:
```kotlin
fun clearRemoteVideoView() {
    remoteVideoView?.let { view ->
        remoteParticipants.values.forEach { participant ->
            participant.remoteVideoTracks.forEach { publication ->
                publication.remoteVideoTrack?.removeSink(view)
            }
        }
    }
    remoteVideoView = null
    Log.d(TAG, "🗑️ Remote VideoView cleared")
}
```

By removing the sink *before* the surface is dismantled, we sever the connection between the background frame pipeline and the graphics hardware, preventing crashes.

## 5. Gradle, NDK & ABI Compilation Mismatches

Integrating native pre-compiled library binaries (such as WebRTC C++ cores packaged in Twilio's `.aar` modules) can trigger compilation bottlenecks.

### Symptoms
- Gradle build failure with: `Cannot path match native libraries for architecture x86_64 or arm64`
- Flutter run fails on modern Apple Silicon Macs when building for the Android emulator.

### Root Cause Analysis
Modern mobile devices run on `arm64-v8a` architectures. However, x86 emulators require `x86` or `x86_64` binaries. If a native library does not package compiled binaries for every target CPU architecture (ABI), the build toolchain fails.

### Resolution Configs
Configure the app-level `build.gradle.kts` to specify target ABIs to filter unsupported architectures, and ensure that the NDK version matches Flutter’s required NDK properties:

```kotlin
android {
    defaultConfig {
        ndk {
            abiFilters.addAll(setOf("armeabi-v7a", "arm64-v8a", "x86", "x86_64"))
        }
    }
}
```
This forces Gradle to strip out invalid architectures and construct a clean, compatible binary for either local emulator debugging or physical device deployment.
